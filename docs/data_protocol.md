# Local data and execution protocol

No data is supplied or downloaded. Baby/Sports/Clothing are dataset names, not a guarantee of equivalent Amazon releases or splits. Supply zero-based user/item IDs with explicitly declared catalog sizes. Features must have exactly one row per declared item ID; mapping correctness cannot be inferred from matrix shape and must be checked by the data owner.

The JSON manifest schema is strict. Copy configs/dataset/manifest.example.json beside external data and replace its placeholder dimensions, declarations and hashes; it is not a runnable dataset. Required root keys: n_users, n_items, metadata, files. All metadata fields are nonempty strings: dataset, source, version, filtering, split_protocol, id_mapping, encoders, mask_protocol. Unknown versions must be declared as unknown (user supplied), not guessed. id_mapping should describe/reference the exact mapping and its hash; encoders describes each feature encoder/version and dimension. mask_protocol records natural-missing definition, experiment pattern/rate/seed and train-time vs inference-time missingness.

files must contain train, valid, test, visual, text, natural_mask, experiment_mask. Each descriptor has path and the actual SHA256, plus key for NPZ only. Paths resolve relative to the manifest, may point to the user's external data, and are never downloaded. Each file hash is checked before reading. NPY/NPZ are loaded without pickle; object arrays (including ragged ChaoRec files) must be converted offline to the explicit numeric format. Example shape of one descriptor:

```json
{"path": "train.npy", "sha256": "REPLACE_WITH_ACTUAL_SHA256"}
```

Edge arrays: integer [E,2]. Alternatively edges may be CSV with exactly `user,item` header. Features: floating [I,D], D>0. Masks: boolean [I,2], columns image then text. Effective visibility is natural_mask AND experiment_mask; preserve both on disk. Do not infer missingness from feature zeros. Nonfinite currently observed features are rejected, hidden values are sanitized before projection. Fixed masks can be generated with data.fixed_mask (explicit seed and independent/coupled/visual/text pattern), saved by the user, and then hashed in the manifest. The framework does not silently generate or replace evaluation masks.

To import MMRec x_label data, replace all three split descriptors with mmrec_inter, with path/sha256 and optional user_field, item_field, label_field, separator (defaults userID, itemID, x_label, TAB). Labels 0/1/2 are TRAIN/validation/test. IDs must already be independent zero-based IDs. No MMRec training or search code is reused. ChaoRec's offset item IDs are not automatically guessed; subtract the documented offset during an explicit owner-reviewed conversion, then record the mapping.

Duplicate pairs within a split and overlaps across splits are errors. Graph construction separately deduplicates TRAIN pairs defensively. Empty TRAIN is rejected; the training CLI also requires nonempty validation/test. Cold users are retained and produce zero representations (ties ranked by lower item ID); no silent filtering is performed. Cold items retain content but no random ID signal or donor transport. Catalog sizes include declared isolated IDs.

Cold/warm is defined strictly by zero/positive TRAIN degree, separately for users and items. provenance.evaluation_coverage contains valid/test distinct target-user/item counts, cold distinct endpoint counts, interaction counts involving cold users/items/either/both, and whole-catalog zero-degree counts. evaluate(return_report=True) reports metrics and the same coverage; the CLI records it in validation logs, selection metadata and final-test metadata. A zero user vector yields all-zero scores and deterministic item-ID tie-breaking, not learned cold-user preference. Do not report aggregate scores as evidence of solved cold-start.

training.evaluation_population=all is the default; warm_only is a strict assertion that every validation/test target endpoint has positive TRAIN degree. Loader/evaluator reject violations instead of filtering. Even warm_only keeps all declared catalog items as candidates; it does not redefine the catalog or graph. No new cold-start model or imputed user representation is added.

Evaluation uses all catalog items, including declared cold items. Validation always masks TRAIN. Test masks TRAIN by default; training.test_mask_valid=true explicitly adds validation history, without adding validation interactions to model support. Targets overlapping the exclusion set are errors. Only users with at least one target enter macro-average Recall/NDCG; ideal DCG uses min(k, number of targets). Fewer than k eligible candidates produce -1 sentinels, which count as misses. Exact ties use ascending item ID. Both user and item chunks bound score memory, with fixed embeddings computed once per evaluation.

The training CLI uses one BPR+L2 optimizer stage and one newly sampled modality-drop view per batch, shared by both modules. Dropout never reveals a naturally/experimentally hidden feature. Evaluation uses the original fixed mask with no dropout. Negative sampling only excludes TRAIN; validation/test positives are deliberately not consulted. Full-graph encoding is repeated per batch, so scalability and training runtime remain unverified. Sparse memory is O(E*d), not O(I²), but large E may still exceed memory.

training.protocol is explicitly mtmt (default) or ftmt. MTMT constructs the model with natural_mask AND experiment_mask; FTMT constructs it with natural_mask. Training dropout can only remove from that base. Both validation and final test pass the same fixed natural_mask AND experiment_mask to encode; donor/LOO statistics are rebuilt using that view on the same unchanged TRAIN incidence. FTMT full means all naturally available content, not fabricated naturally missing content. Loader finiteness checks use the actual training visibility (natural for FTMT), not just evaluation visibility. The protocol is written to resolved configuration, provenance and final-test metadata. Neither mask is derived from test labels; the user supplies fixed mask files and hashes.

Each training batch repeats all-item projections O(I*(Dv+Dt)*d), shallow CF O(L*E*d), and both transport modules O(E*d+(U+I)*d). With ceil(E/batch_size) batches this work repeats that many times per epoch. Stored raw features cost O(I*(Dv+Dt)), IDs O((U+I)*d), and intermediate membership tensors O(E*d) plus autograd storage. No claim of large-scale speed, measured memory fit, or GPU throughput is made.

For an explicit user-run CUDA device, configure_determinism checks that CUDA is not yet initialized, sets process-local CUBLAS_WORKSPACE_CONFIG=:4096:8 if absent (or accepts :16:8/:4096:8), and rejects invalid preexisting values before seeds/device transfer. It then enables deterministic algorithms. An already initialized CUDA process is rejected; start a fresh process. This is runtime code for the user's authorized environment, not an environment change performed on the development computer. Other unsupported deterministic kernels may still raise; GPU operation remains untested.

Public model APIs accept one-dimensional int32/int64 ID arrays, with explicit nonnegative catalog range checks. Paired scoring and all three loss arrays must have identical shapes; loss batches must be nonempty. Broadcasting, float/bool IDs and negative Python-style indexing are rejected. Explicit integer empty vectors are supported for prediction only. Catalog counts must be positive Python integers (not bool), and numeric configuration values must be finite int/float values excluding bool.

Construction normalizes all model tensors onto CPU, with floating state in float32; move the complete model with model.to(device) afterwards, or model.double() for float64. IDs and boolean view masks are validated and safely moved to the model device. Caller-provided encoded tensors must match model device/dtype and exact catalog dimensions. Only float32/float64 execution is supported: half, bfloat16 and active CPU/CUDA autocast are explicitly rejected, including zero-vector normalization. No GPU or mixed-precision validation has been performed; no AMP support is claimed.

Checkpoint and stopping decisions use validation only. The selected trainable parameters are reloaded and test is evaluated once after the loop. Features/support are reconstructed from hash-checked files, not stored in the parameter checkpoint. This minimal CLI does not support resume or hyperparameter search. To compare external runs, choose configuration only by validation and keep test results out of that choice. Record the same fixed masks and candidate policy for all baselines.

Each user-run output stores resolved_config.json, provenance.json (original manifest plus hashes), environment.json (versions, commit/dirty state), validation.jsonl, selection.json, selection_binding.json and best.pt; only the separately invoked evaluate.py writes final_test.json. Runtime artifacts must stay external/untracked. The CLI flag is an explicit opt-in, not permission to run it on the prohibited development computer.


main.py performs validation-only training. evaluate.py --run <selected-run> --manifest <manifest> --execute-final-test verifies saved configuration/provenance/checkpoint hashes and parameter contracts before testing. Existing final_test.json is never overwritten. Training and final testing both require separate explicit user actions in an authorized external environment.
